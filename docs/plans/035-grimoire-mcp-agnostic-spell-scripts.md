# 035 — Grimoire MCP-Agnostic Spell Scripts

> Complexity: **Medium**. Source pitch: `brain/Grimoire - MCP-Agnostic Spell Scripts.md` (Shape Up, small batch).
> This is a **prose/script-text rewrite + content-assertion test updates + README doc update**. No new infrastructure, no new components, no UI files touched.

## Goal & scope

Make every shipped meta-spell portable across whatever Obsidian-aware MCP server the user happens to have mounted. The Refine script is the clear break: it names `mcp__obsidian-mcp-tools__*` tools verbatim and tells the model to call them directly, so it silently fails for anyone whose vault MCP differs. The Forge scripts already bind by intent but only accidentally; that discipline gets promoted to an explicit, stated standard.

Three pillars from the pitch:

1. **Capability/intent binding, never server-specific names.** Shipped scripts describe what they need ("read this note", "write this note", "search the vault") and let the model match those to whatever the mounted server exposes. Floor assumption: *some* Obsidian-aware MCP exists, with filesystem (`VAULT_MOUNT_PATH`) as the fallback when MCP is absent or broken.
2. **An explicit search ladder** in Refine (the one capability that genuinely varies): prefer semantic retrieval when the server offers it → degrade to full-text search → degrade again to filesystem grep. Use the best available rung and *say which rung was used*, rather than assuming the top.
3. **Full-file-write edit path only.** Read → modify in context → write the whole file. Deliberately drop the "prefer line-level patches" instruction: surgical-patch contracts differ across unknown servers in ways natural language can't pin down. The cost (losing leave-the-rest-untouched, heavier on big notes) is accepted because it behaves identically everywhere.

Documentation (the "ceiling"): README onboarding recommends a semantic-capable server for best-case search, documents the custom-spell fork seam, and states plainly that best-case search is an opt-in the user reaches for — never a guarantee the plugin makes.

### Out of scope (enforce — straight from the No-Gos)

- **No adapter / shim / translation layer.** Full-file writes stand in for any patch-contract normalisation.
- **No patch-contract abstraction.** Do not build code that reconciles incompatible patch tools.
- **No enumerating known servers or their tool names inside shipped scripts.** The moment a script names a server, it stops being portable. (The README *example* may still show one concrete server for copy-paste setup — that is user-facing config, not shipped-script text. The two are different surfaces; keep the discipline inside the scripts.)
- **No mandating a specific server.** The floor is "some Obsidian MCP", not a named one.
- **No promise of semantic-quality search** to users on non-semantic servers — a documented ceiling, not a plugin guarantee.
- **Remote/Portal transport** stays untouched this cycle.
- **No new components, classes, or files.** Edits land inside the three existing template functions, their test files, and `README.md`.

## Proposed solution

The shipped script bodies are produced by three pure template functions, each rendered to a `.md` file by its materializer on plugin load:

- `renderRefineSystemPrompt()` in `src/refine/refineTemplate.ts` → `<pluginDir>/refine.md` (the clear break; main deliverable).
- `renderForgeSystemPrompt(input)` in `src/forge/forgeTemplate.ts` → `<vault>/.../forge.md` (already intent-bound; codify the standard explicitly).
- `renderForgeUpdateSystemPrompt(input)` in `src/forge/forgeUpdateTemplate.ts` → forge-update prompt (intent-bound but still says "prefer line-level patches"; switch to full-file-write).

The capability ladder is **prose inside the Refine string**, not branching code — the model reads its own tool list and picks the rung. This is the correct shape per the pitch; a code-level ladder would be exactly the adapter layer the No-Gos forbid (see Technical notes).

Where the script text is generated by code there are assertable invariants. The honest split:

- **Mechanically assertable** (becomes a content-assertion test): presence/absence of specific substrings — e.g. "the Refine body contains no `mcp__obsidian-mcp-tools__` server-prefixed tool name", "the body contains semantic→full-text→filesystem ladder language", "the body instructs full-file write and no longer prefers line-level patches".
- **Prose-only, no meaningful automated test**: the *quality* and *clarity* of the rewritten instructions. These todos are flagged prose-only; their only gate is that the file still renders a non-empty string and the existing structural assertions (mode headings, execution-mode callout, etc.) still hold.

## Data flow

Unchanged. `onload` → materializer calls `render…SystemPrompt()` → writes `.md` → cast dispatch points Claude Code at the file → the model reads the (now portable) instructions and binds tools by capability against whatever server is mounted. This feature only changes the *text* that flows through that pipe; no wiring changes.

## Error handling

No code error paths change. The script-level "error handling" is the fallback ladder itself, expressed as model instructions:

- MCP absent/broken → fall back to filesystem rooted at `VAULT_MOUNT_PATH` (already present; preserved).
- No semantic search tool → degrade to full-text; no full-text → degrade to filesystem grep (new ladder).

The accepted soft risk (model-compliance dependency: the model must read its tool list and reach for semantic when present) is explicitly accepted per the pitch — blast radius is degraded search, not a broken pipeline, and it is the same judgment the existing MCP-vs-filesystem fallback already relies on. No code guards this; it is a prose instruction.

## Technical notes

- **Patterns considered and rejected (design-patterns pass):**
  - *Strategy / Chain of Responsibility for the search ladder* — **rejected**: the ladder is a natural-language instruction the model evaluates at runtime against its tool list, not branching code in the plugin. Encoding it as code would require the plugin to know the mounted server's tools, which is precisely the server-enumeration the No-Gos forbid. YAGNI + No-Go.
  - *Adapter / shim to normalise patch contracts* — **rejected**: explicit No-Go. Full-file writes sidestep it entirely.
  - *Template Method to share the Spell-Wrapper envelope across the three templates* — **rejected**: the three bodies already duplicate the `%%`-block envelope as inline strings, but this is **2 occurrences of a stable shape, not 3+ diverging ones**, and the bodies differ substantially. Per KISS-over-DRY tie-breaker, no extraction this cycle. Flag only; do not act.
- **Design-rubric §7:** every component has one reason to change (its shipped script's prose). No new abstractions. Dependency direction unchanged (templates are pure leaves; materializers at the edge depend on them). Testability: each is a pure string-returning function; content assertions are the right tool. The honest gap — prose *quality* is not automatable — is called out per-todo.
- **The Refine test file currently pins the bug.** `tests/refine/refineTemplate.test.ts:51-55` asserts `search_vault_simple`/`search_vault_smart` are present, and `:84-89` asserts "line-level patch" is present. Both assertions **invert** under this feature. The dev agent must rewrite those specific tests, not merely add new ones — leaving them green would mean the rewrite didn't land.
- **README is a different surface from the shipped scripts.** The README MAY keep a concrete server example for copy-paste setup (it currently shows Local REST API's `mcp__obsidian__*` tools, lines 39-44, with a "must match the server name you registered" caveat at line 63). The shipped-script no-server-name discipline does **not** apply to README config examples. Do not strip the README's example; *add* the semantic-server recommendation and the fork-seam note around it.
- **Concrete bug evidence:** the shipped Refine script names `mcp__obsidian-mcp-tools__*` while the README tells users to register a *different* server (`obsidian`, via Local REST API, exposing `mcp__obsidian__*`). The Refine script references tools the README never tells anyone to install — the exact silent-failure the pitch describes.
- **Custom-spell fork seam already exists:** `CustomRefineSeeder` + the `sentinel: refine` mechanism (see `docs/features/custom-refine-spell.md`) let a user fork the Refine default into a note that targets their own tools precisely. The README doc todo points users at this seam; no code is needed.
